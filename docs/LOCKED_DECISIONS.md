# Pulumi + Python port — five decisions, critiqued and locked

Date: 2026-09-16. Sources: the repository at `/Users/isaiulate/git/personal/devops/terraform-aws-static-site` (read-only; file:line references are to the working tree as of `fabcd79` plus the four staged comment-only edits), Pulumi documentation fetched today, and the Pulumi CLI source on `master` today (`pkg/backend/diy/{backend,lock,state,meta}.go`, `pkg/secrets/cloud/manager.go`). Current versions read from GitHub/PyPI today: Pulumi CLI v3.263.0, `pulumi-aws` 7.46.0 (bridged from terraform-provider-aws v6.64.0 — the same v6 generation `~> 6.61` pins in `bootstrap/versions.tf:42`), `pulumi-policy` 1.21.0, `pulumi/actions` v7.0.0, uv 0.12.15, ruff 0.16.8, mypy 2.3.1, zizmor v1.30.1.

The operating model the port must keep (README.md:3-22): every environment is applied, verified and destroyed inside the hour; reproducibility from zero and verifiable teardown are the goals; anything that blocks or survives destroy is a defect; CI is OIDC-only, `plan` role on PRs, one `apply` role per environment trusting one `environment:` subject; the app repository deploys through a role this repo creates and destroys with the environment (`docs/DEPLOY_CONTRACT.md`).

## 1. State backend and secrets encryption

### (a) Proposed
Self-managed `s3://` Pulumi backend in the user's account, with a KMS key created by the bootstrap and used as `--secrets-provider awskms://...`. Alternative: Pulumi Cloud.

### (b) Critique

**The KMS half contradicts a decision this repository already made, in writing, for this exact reason.** `bootstrap/state.tf:106-126` rejects a customer-managed key for the state bucket because "a CMK can't be deleted synchronously — aws_kms_key enforces a minimum seven-day deletion schedule — so it would be the only resource in this repository that `destroy` can't actually remove immediately", and the bootstrap teardown (`docs/TEARDOWN.md` §8) is "back to an empty account". A KMS key created for `awskms://` is the same resource with a different job; `docs/TEARDOWN.md:833-836` would gain a "key pending deletion until next week" exception. The proposal re-introduces the one thing the design argued out.

**There is nothing for the key to encrypt.** Every input is committed and non-sensitive by design (`bootstrap/variables.tf:9-11`, `bootstrap/terraform.tfvars` header: "no account id, no ARN, no key, no token"); the SSM parameters are `String`, not `SecureString`, and the test suite pins that (`modules/static-site/tests/plan.tftest.hcl:593`); Terraform state itself sits plaintext under SSE-S3. Pulumi encrypts *only values marked secret* — "Only values explicitly marked as secrets are encrypted ... Resource physical IDs ... always stored in plain text" (pulumi.com/docs/iac/concepts/secrets/). With zero secret values, the secrets provider is an obligation without a payload. It cannot be omitted, though: every stack has one, and the DIY default is `passphrase`, prompted interactively.

**`awskms://` puts a KMS call on every preview, including the read-only plan role's.** Verified in source: `pkg/secrets/cloud/manager.go` `newCloudSecretsManager` calls `keeper.Decrypt(...)` on the encrypted data key *at construction*, before any secret value is touched. So the plan role would need `kms:Decrypt` on the key, a grant the Terraform plan role never held (`bootstrap/oidc.tf:799-856` grants S3 only), and the bootstrap would need a key policy naming three roles. It also writes the key's ARN — which embeds the account id — into the committed `Pulumi.<stack>.yaml` (`secretsprovider:` + `encryptedkey:`), which `envs/stage/main.tf:57-60` names as "the material this repository's push protection exists to catch". The passphrase provider commits only an `encryptionsalt`, which is not sensitive.

**Locking: Pulumi's DIY backend never used DynamoDB, and there is no DynamoDB option to decide about.** Verified in `pkg/backend/diy/lock.go`: `Lock()` writes `.pulumi/locks/<fully-qualified stack>/<uuid>.json`, lists that prefix, and `Unlock()` deletes it; a stale lock is cleared by `pulumi cancel`. The docs: "A basic file-based locking system is enabled by default for all DIY backends" (pulumi.com/docs/iac/operations/stack-management/using-a-diy-backend/). Two consequences the proposal did not price:
- `Preview` does **not** take the lock (`backend.go:1204-1208` goes straight to `backend.Preview`; `Update`, `Refresh`, `Destroy` and non-preview `Import` call `b.Lock`). Two PR previews of the same stack can run concurrently; no `.tflock` write is needed by the plan role (decision 5).
- A `pulumi up`/`destroy` writes more than Terraform does: the checkpoint `.pulumi/stacks/<project>/<stack>.json`, a `.bak` beside it (`state.go` `backupTarget`), a timestamped copy under `.pulumi/backups/<project>/<stack>/`, and `.history.json` + `.checkpoint.json` under `.pulumi/history/<project>/<stack>/` (`state.go:490-520, 690-714`). Nothing prunes backups or history. On the versioned bucket `state.tf:141-185` argues for, that is an accumulation problem larger than the `.tflock` one it was written for — but a *solvable* one, because these are prefix-addressable and S3 lifecycle filters by prefix (the `.tflock` suffix problem at `state.tf:151-155` does not recur). `PULUMI_DIY_BACKEND_DISABLE_CHECKPOINT_BACKUPS` (checked in `backupStack`) removes the backups class outright.

**Layout is not a free choice in 2026.** `backend.go:363-378`: legacy (non-project) DIY state now *errors* — "Legacy DIY state is deprecated ... due to be removed in a future release before the end of this year (2026)" — unless `PULUMI_DIY_BACKEND_IGNORE_DEPRECATION_ERROR=1`. A fresh empty bucket gets project mode automatically (`meta.go` `ensurePulumiMeta` writes `.pulumi/meta.yaml` version 1). That first login is therefore a **write**, and it has to be made by the bootstrap's elevated identity, not by CI: a plan role landing on a bucket with no `meta.yaml` fails at `PutObject`.

**Stacks must pre-exist.** `pulumi preview` needs a selected stack; `pulumi stack init` writes the checkpoint file. Terraform had no equivalent step (the S3 backend creates the key on first write). So the bootstrap must `pulumi stack init` each environment once. After `pulumi destroy` the checkpoint stays (empty) — the analogue of Terraform emptying rather than deleting state (`oidc.tf:1155-1160`) — and `pulumi stack rm` / `destroy --remove` are the operations to withhold `s3:DeleteObject` from.

**How `backend "s3" {}` filled at init maps.** `envs/stage/backend.tf:23-25` keeps the block empty because the bucket name is per-account, and CI passes `-backend-config=` from repository variables (`plan.yml:366-375`). Pulumi's equivalents: `PULUMI_BACKEND_URL` env var (takes precedence over the logged-in backend; pulumi.com/docs/iac/cli/environment-variables/), or `backend: url:` in `Pulumi.yaml`. The committed `Pulumi.yaml` must therefore carry **no** `backend.url`; CI sets `PULUMI_BACKEND_URL=s3://<bucket>?region=<r>&awssdk=v2` from a repository variable (the analogue of `TF_STATE_BUCKET`), locally `pulumi login` once (stored in `~/.pulumi/credentials.json`, outside the tree, so nothing to gitignore). Per-environment `Pulumi.<env>.yaml` is committed (it is the analogue of `envs/<env>/terraform.tfvars`, `.gitignore:16` un-ignores those) with its `encryptionsalt`.

**Pulumi Cloud.** Pricing page today: Free is "$0", "1 user", "Unlimited projects, stacks, and environments", "OIDC support (available across all tiers)"; policy enforcement is "Manual" on Free and custom packs/preventative policies are Pro+. Cost is not the objection. The objections are the operating model's: state and the audit trail leave the user's AWS account (README.md:7 "in your own AWS account"); the "empty account" claim (`docs/TEARDOWN.md` §8) can no longer be settled by an AWS sweep because a stack record survives in a SaaS; CI needs either a long-lived `PULUMI_ACCESS_TOKEN` (the class of secret `oidc.tf:4-8` exists to have none of) or a second OIDC trust to configure. Reject for this port; note it as the correct answer for a *durable* deployment, alongside the README's own "separate accounts" line (README.md:455-456).

**Cost.** S3 only; identical shape to today's line item (README.md:356). No KMS charge because no key.

### (c) Revised recommendation
- Backend: `s3://<name_prefix>-pulumistate-<8 hex>?region=<region>&awssdk=v2`, bucket created by the bootstrap with the same posture as `state.tf` (versioning, SSE-S3, public-access block, `BucketOwnerEnforced`, TLS-only policy, `protect=True`), plus lifecycle rules **by prefix** on `.pulumi/backups/` and `.pulumi/history/` (expire current versions after N days) in addition to the noncurrent/delete-marker rule inherited from `state.tf:156-185`. Set `PULUMI_DIY_BACKEND_DISABLE_CHECKPOINT_BACKUPS=1` in every workflow and in the Makefile so the backups class is never written by CI; history stays because `pulumi stack history` is the audit trail the design wants.
- Secrets provider: **`passphrase`**, not `awskms`. The passphrase lives in one GitHub repository *secret* (`PULUMI_CONFIG_PASSPHRASE`) and one local env export; document that it protects nothing today (no secret values exist) and that `pulumi stack change-secrets-provider "awskms://..."` is the documented upgrade for a durable deployment, with the seven-day deletion cost stated where `state.tf:106-126` states it. Do **not** use an empty passphrase (pulumi/pulumi#9612, closed: set-but-empty is not honoured). Fork-PR offline previews (decision 3) use a literal throwaway passphrase because their stack lives only for the job.
- Bootstrap creates: the bucket, then performs the first `pulumi login s3://...` (writes `.pulumi/meta.yaml`, project mode) and `pulumi stack init <env>` for each environment, printing the `PULUMI_BACKEND_URL` line the way `outputs.tf:17-33` prints `backend_init_command`. The bootstrap's own stack uses a `file://` backend at a gitignored path under `bootstrap/` (the analogue of local `bootstrap/terraform.tfstate`, `state.tf:1-12`), with the same "back it up" instruction as `docs/BOOTSTRAP.md` §4.
- Cloner with an empty account needs: AWS CLI v2 with `export-credentials` (unchanged, `docs/BOOTSTRAP.md:83-101`), `pulumi` at the pinned version, `uv`, `gh`; nothing else and no third-party account.

### (d) LOCKED
**LOCKED-1:** Self-managed S3 DIY backend in the user's account (project-scoped layout, no DynamoDB — lock objects under `.pulumi/locks/`), `passphrase` secrets provider held in one repository secret, **no KMS key** (a CMK's seven-day deletion window is the exact defect `state.tf:106-126` refused, and there are no secret values for it to protect); the bootstrap creates the bucket, performs the first login that writes `.pulumi/meta.yaml`, and initialises each environment's stack.

**Amended 2026-09-16** (mechanism, not substance — docs/PLAN_CRITIQUE_2026-09-16.md F1, F9, F10): the first `.pulumi/meta.yaml` write is made by the first *backend construction* under the `s3://` URL, which is the bootstrap identity's `pulumi stack init <env>` run with `PULUMI_BACKEND_URL` set inline — **no `pulumi login` anywhere**, because an exported `PULUMI_BACKEND_URL` silently wins over a login (measured: with `file://A` exported, `pulumi login file://B` succeeds and every later command still uses `A`). `stack init` also writes `<env>.json.bak` beside the checkpoint and takes a transient lock, so the post-bootstrap bucket holds five objects, not three. And "there are no secret values for it to protect" is true of the inputs only: `ssm.Parameter.value` is schema-secret, and the passphrase is required for *every* operation regardless, because the CLI verifies it against the committed `encryptionsalt` when it builds the secrets manager (measured: `preview` on a never-applied stack fails without it). The decision — DIY S3, passphrase, no KMS, bootstrap identity makes the first write and initialises each stack — holds.

### (e) Not verified
- That `PULUMI_CONFIG_PASSPHRASE` set to a non-empty literal works with zero interactive prompt on a GitHub runner for `stack init`, `preview`, `up`, `destroy` in the current CLI — inferred from docs and the closed issue, not run.
- Whether `.pulumi/meta.yaml` is ever re-written by a later CLI on read (source suggests read-only once present; not exercised against S3).
- The exact bucket object count per `up` on the current CLI (derived from source; not measured against a bucket).

## 2. Bootstrap ownership and the single OIDC provider

### (a) Proposed
Same AWS account as the Terraform repository; the Pulumi bootstrap *looks up* the existing GitHub OIDC provider rather than creating it, and creates its own plan/apply roles, state bucket, KMS key and permissions boundary.

### (b) Critique

**"Look up" breaks reproducibility from zero by construction.** README.md:99-101 and `docs/BOOTSTRAP.md:1-40` are "written for someone who has cloned this and has nothing else". A bootstrap that only looks the provider up fails in an empty account with a not-found that names nothing — and the Terraform bootstrap owns the provider today (`bootstrap/oidc.tf:52-60`), so the proposal makes the Pulumi repository's CI depend on the Terraform repository's bootstrap staying up. `docs/BOOTSTRAP.md:141-143` already warns from the other side: "a subsequent `terraform destroy` of the bootstrap would then delete a provider you did not create; if the account shares it, remove it from state". The README's from-zero walk ends with bootstrap teardown (README.md:333-336); do that on the Terraform side and the Pulumi side's plan, apply and app-deploy trust all fail at `AssumeRoleWithWebIdentity` with "an error message that gives no hint why" (`oidc.tf:69-74`).

**The `import_` resource option is not create-or-import.** Docs (pulumi.com/docs/iac/adopting-pulumi/import/, read today): with `pulumi.ResourceOptions(import_=<arn>)`, "If the resource isn't found, the preview will fail"; if found, the engine imports and then "issue[s] an update step to reconcile the differences". So `import_` left permanently in the program is a bootstrap that fails in an empty account — the opposite failure to lookup. A probe-then-branch (`try: aws.iam.get_open_id_connect_provider(...) except: create`) is worse: on the run *after* this stack created the provider, the probe finds it, the program stops declaring it, and Pulumi plans to **delete** the provider it created. Exception-driven control flow around a resource's existence is not an adoption strategy.

**`pulumi import` (CLI) maps exactly onto today's runbook step.** `docs/BOOTSTRAP.md:135-143` and `oidc.tf:41-50` already tell a cloner to `terraform import aws_iam_openid_connect_provider.github arn:...:oidc-provider/token.actions.githubusercontent.com` on `EntityAlreadyExists`. `pulumi import aws:iam/openIdConnectProvider:OpenIdConnectProvider github <arn>` is the same step (the 2021-22 import bugs pulumi/pulumi#8632 and pulumi-aws#1748 are closed). The remaining question is which owner is *default*, and that must be a declared stack config value, not a probe.

**Name collisions in a shared account are real, and two of them are contract-fixed.** Names read from the tree, with the developer's values in `bootstrap/terraform.tfvars` / `envs/stage/terraform.tfvars` (`name_prefix = "isai2105"`, `project = "terraform-aws-static-site"`):

| Terraform name | Where | Collision class |
|---|---|---|
| `<name_prefix>-tfstate-<hex>` | `state.tf:28` | avoided by a different prefix |
| `<name_prefix>-ci-plan`, `<name_prefix>-ci-apply-<env>` | `oidc.tf:617, 1107` | IAM role names are account-global; **hard** collision if the prefix is reused |
| `<name_prefix>-app-deploy-boundary` | `oidc.tf:371` | same |
| `<name_prefix>-site-<env>-<hex>` (bucket; also the `Name` tag, log-group suffix, OAC and function names) | `modules/static-site/s3.tf:37`, `oidc.tf:400-407, 517-522` | avoided by a prefix that does not *extend* the Terraform one: the apply roles grant on `<name_prefix>-site-*` (`oidc.tf:162-167`), so a Pulumi prefix of `isai2105` + anything would still have to avoid `isai2105-site-`. `isai2105-pulumi-site-…` does not match `isai2105-site-*`. |
| `/static-site/<env>/{bucket_name,cloudfront_distribution_id,site_url}` | `modules/static-site/ssm.tf:108` | **contract-fixed** (`docs/DEPLOY_CONTRACT.md:232-238`); no prefix in it |
| `react-cloudfront-app-deploy-<env>` | `modules/static-site/iam.tf:137`; `docs/DEPLOY_CONTRACT.md:56-81` | **contract-fixed**; IAM role names are account-global |
| tags `Project`, `Env=<env>`, `ManagedBy=terraform` | `bootstrap/providers.tf:12-23`, `envs/stage/providers.tf:30-43` | `Project` differs; `Env=stage` is shared but every sweep filters on `Project` **and** `Env` (`e2e.yml:1236-1238`) |
| cache/response-headers policy quotas, 20 per account | README.md:270-277 | shared; 4 per standing environment per repo |

The two contract-fixed names mean the same account **cannot hold `stage` from both repositories at the same moment**: the second `CreateRole` returns `EntityAlreadyExists`, and the second SSM `PutParameter` either fails or overwrites the other repository's discovery values — the app repository reads them at deploy time (`DEPLOY_CONTRACT.md:239-244`) and would deploy into the wrong bucket. Nothing in either repository detects that. Because environments are ephemeral this is a serialisation rule rather than a design blocker, but it has to be written down, and the Pulumi `verify-teardown` analogue must query on its own `Project` value so it never reports the other repository's standing environment as its own leak.

### (c) Revised recommendation
- **Preferred: a separate AWS account** for the Pulumi port. The README's own tradeoff says "Separate accounts are the correct answer for anything durable" (README.md:455-456); here it also makes the OIDC-provider question disappear (the bootstrap creates it, exactly as `oidc.tf:52-60`), removes every collision in the table, and keeps both repositories' from-zero walks independent.
- **If the account must be shared:** the bootstrap takes one explicit stack config value `oidcProvider: create | adopt` (default `create`, so a fresh clone in an empty account is reproducible). `create` declares `aws.iam.OpenIdConnectProvider` with `client_id_list=["sts.amazonaws.com"]` and no thumbprint (mirrors `oidc.tf:33-40`). `adopt` declares nothing and resolves the ARN by composition from `get_caller_identity` + `get_partition` (the shape `envs/stage/main.tf:62-68` uses, never the `url` lookup form, for the reason given at `main.tf:47-55`). `pulumi import` is the documented step for a cloner who wants the Pulumi stack to *own* a pre-existing provider. The runbook states the cross-repository coupling in both directions where `docs/BOOTSTRAP.md:141-143` states its half.
- Namespace: `name_prefix` must not begin with the Terraform repository's `name_prefix` followed by `-site` (validate: reject a prefix that is `<tf_prefix>` or `<tf_prefix>-site*`; recommend `<owner>-pulumi`), state bucket infix `-pulumistate-`, `Project` tag = the new repository's name, `ManagedBy = "pulumi"`. Environment names, the SSM path and the deploy role name stay exactly as the deploy contract fixes them; the runbook adds the rule "one repository's `<env>` standing at a time in a shared account" beside the quota note (README.md:270-277).
- The bootstrap creates its own plan role, per-environment apply roles, state bucket and boundary policy (no KMS key — decision 1).

### (d) LOCKED
**LOCKED-2:** Prefer a separate AWS account; in a shared account the bootstrap takes an explicit `oidcProvider: create|adopt` config (default `create`, so an empty account reproduces from zero), never a probe and never a permanent `import_`; `pulumi import` remains the runbook step for adoption; the Pulumi namespace is `<owner>-pulumi` as `name_prefix` (rejecting any prefix that extends `<tf_prefix>-site`), `-pulumistate-` for the bucket, its own `Project` tag and `ManagedBy=pulumi`; the SSM path `/static-site/<env>/…` and role `react-cloudfront-app-deploy-<env>` are contract-fixed and force the rule that only one repository's `<env>` stands at a time.

### (e) Not verified
- Whether the app repository's dispatch workflow accepts an environment name other than `stage`/`prod` (out of scope of this tree; `DEPLOY_CONTRACT.md:63` says `<env>` is `stage` or `prod`). If it does not, the "one at a time" rule is the only option in a shared account.
- `pulumi import` of `aws:iam/openIdConnectProvider` on `pulumi-aws` 7.46.0 was not run.

## 3. Test strategy

### (a) Proposed
Pulumi unit tests with `pulumi.runtime.set_mocks` under pytest.

### (b) Critique

**What the Terraform suite proves, precisely.** `plan.tftest.hcl:11-45`: the real AWS provider is configured with literal fake keys plus `skip_credentials_validation`, `skip_requesting_account_id`, `skip_metadata_api_check`, every run block is `command = plan`, and the suite "passes with no HOME, no AWS variables of any kind and every outbound HTTP request black-holed". Its assertions read plan-time-known values the provider computed — schema defaults, the `region` attribute that proves which alias a resource is bound to (`:70-84`, `:343-348`), composed names, policy wiring — and it deliberately rejects `mock_provider` because it "replaces the provider's own plan behaviour with values Terraform invents ... a suite that passes by agreeing with its own mocks" (`:57-66`).

**`set_mocks` is `mock_provider`.** Pulumi's docs: the `new_resource` handler "receives input properties ... and must explicitly return output properties (computed by cloud providers)"; "Lifecycle hooks and transforms are not executed in mock tests" (pulumi.com/docs/iac/guides/testing/unit/). No provider plugin is loaded, so no schema validation, no defaults, no computed `region`, no `Check` of the inputs against terraform-provider-aws. The guarantee lost is the one the required check exists for: *the provider accepts this configuration*. A `set_mocks` suite would have been green for a mis-typed `origin_access_control_origin_type`, a missing `us-east-1` provider on the log delivery, or a `CustomErrorResponse` block — three things `plan.tftest.hcl:248, 343, 622` catch today.

**`pulumi preview` can run with no credentials, in the same shape the tftest uses.** `pulumi-aws` exposes the same three flags on its `Provider` (`sdk/python/pulumi_aws/provider.py:47-50`: `skip_credentials_validation`, `skip_metadata_api_check`, `skip_requesting_account_id`) plus `access_key`/`secret_key`; with placeholder keys and `AWS_EC2_METADATA_DISABLED=true` a preview makes no AWS call (the pattern is documented in pulumi-aws issues and the registry configuration page). Two things make it fully offline: run it against a `file://` backend (`pulumi login file://$RUNNER_TEMP/state`) with a throwaway stack and a literal passphrase, and keep every invoke that needs an account (`get_caller_identity`, `get_partition`, `get_open_id_connect_provider`) **out of the component**, passed in as config — exactly the carve-out `envs/stage/main.tf:14-21` makes for the same reason. The provider plugin binary still downloads (as `terraform test` downloads providers), so a fork PR runner can do it. This preview exercises the bridged provider's `Check` against the upstream v6 schema and yields plan-time-known inputs and defaults; unknowns (the `random` suffix, ARNs, ids) are unknown, as in Terraform.

**Assertions on that preview: two tiers, both free and both offline.**
- CrossGuard policy pack in Python, run with `pulumi preview --policy-pack ./policy`. Verified: the Policy SDK is Apache-2.0 and the CLI runs packs "free of charge, with the caveat that the policy must be present on disk" (crossguard FAQ); the Free tier's "Manual" enforcement gate applies only to Pulumi Cloud–managed packs. A `mandatory` policy fails the preview, so the job goes red on the composition itself (`:747` deploy-role name, `:757` boundary ARN, `:762` subject byte-for-byte, `:576-593` three `String` parameters at `/static-site/<env>/…`, `:248` no custom error responses, `:263` one viewer-request association, `:473-523` both response-headers policies carry CSP/HSTS/nosniff and *different* Cache-Control). Caveat that mirrors `plan.tftest.hcl:538-548`: a policy that reads an unknown at preview is *skipped with a warning* in Pulumi (crossguard core-concepts: "During preview, the validation ... will be skipped, and a warning is emitted"), where Terraform aborts the run block. Policies must assert only plan-known inputs — names, types, counts, wiring — and the job must treat a skipped policy as a failure (grep the warning) so the weaker failure mode cannot pass silently.
- `pulumi preview --json` parsed by pytest for the assertions that are awkward as policies (set equality of parameter names, "exactly two cache policies", alias binding via the resource's `region` input). This is the `terraform show -json` shape the repository already uses in `apply.yml:831` and `e2e.yml:618`.

**Unit tests with mocks keep a narrower job.** Pure-Python composition — the subject string, the role name, the boundary ARN, the CSP constant, input validation that replaces `variables.tf` `validation` blocks — is cheap to pytest without mocks at all (functions, not resources). Where a ComponentResource's wiring is the thing under test, `set_mocks` is acceptable as a *fast* tier, never as the required check.

### (c) Revised recommendation
Required PR check = `preview-offline`: `file://` backend, throwaway stack, literal passphrase, fake-key provider config with the three `skip_*` flags for **both** provider instances (default region and `us-east-1`, mirroring `plan.tftest.hcl:129-171`), `pulumi preview --policy-pack ./policy --non-interactive`, followed by pytest over `pulumi preview --json`. Plus `pytest` unit tests for pure composition logic. `set_mocks` tests are optional and not required. The apply-trap half of the tftest (`:29-38`: a run block that forgot `command = plan` would apply with fake keys and fail loudly) maps to the offline job never holding an OIDC token and to the fake keys, so a mistaken `pulumi up` in that job fails at the provider rather than creating anything.

### (d) LOCKED
**LOCKED-3:** The required fork-safe PR check is a credential-free `pulumi preview` against a `file://` backend with the real `pulumi-aws` plugin configured with placeholder keys and the three `skip_*` flags on both providers, gated by a Python CrossGuard policy pack (`--policy-pack`, mandatory level, skipped-policy warnings treated as failure) and pytest assertions over `pulumi preview --json`; `set_mocks` unit tests are a fast optional tier, not the guarantee.

**Amended 2026-09-16** (mechanism, not substance — docs/PLAN_CRITIQUE_2026-09-16.md F4–F7, F11): the "skipped-policy warning" is an `[advisory]` entry in the plain-text `Policies:` block reading `can't run policy '<name>' from policy pack '<pack>' during preview: <type> value at .<prop> can't be known during preview`; it is on stdout, not stderr, and it is **absent from the `--json` document** (which carries only `steps`, `diagnostics`, `duration`, `changeSummary`, and no stack outputs). The check therefore runs each variant twice — a plain preview grepped for that line, then a `--json` preview for pytest — and every policy reads only preview-known props (camelCase names; anything derived from the random suffix or a resource ARN, including every rendered policy document, is unknown and belongs to the unit tier over the pure builders). The decision — real plugin, placeholder keys, mandatory pack, skipped policy = failure, pytest over the JSON, mocks optional — holds.

### (e) Not verified
- That the current `pulumi-aws` 7.46.0 plugin completes a preview of *this* resource set (CloudFront distribution + logging v2 delivery + function + OAC) with placeholder keys and no network — the pattern is documented for the provider, but not run against these resource types today.
- The exact `pulumi preview --json` schema keys for inputs (`steps[].newState.inputs` is the expected shape; not re-read from the CLI reference today).
- That a skipped-policy warning is emitted in a grep-able, stable form in `pulumi-policy` 1.21.0.

## 4. Toolchain parity

### (a) Proposed
ruff (format+lint), mypy strict, pytest, CrossGuard as the "scan" step, pip pinning via a lock file + Dependabot pip, keep zizmor + the workflow policy audit.

### (b) Critique

**No IaC misconfiguration scanner reads Pulumi Python, verified against each tool's source today.**
- Checkov: `checkov/common/bridgecrew/check_type.py` on `main` lists `terraform`, `terraform_json`, `terraform_plan`, `cloudformation`, `cdk`, `sast_python` … and **no `pulumi`** framework; the "`--framework pulumi` on `pulumi preview --json`" claim that circulates in blog posts is not in the tree.
- Trivy: `pkg/iac/scanners/` on `main` holds `ansible azure cloudformation dockerfile generic helm kubernetes terraform terraformplan` — no Pulumi. Trivy *does* scan `uv.lock` for vulnerable Python packages (since v0.59.0, trivy.dev/docs/latest/coverage/language/python/), which is SCA, not misconfiguration.
- KICS: `docs/platforms.md` — "KICS supports scanning Pulumi manifests with `.yaml` extension" — Pulumi YAML only; useless for a Python program.
- Snyk IaC: supported formats are Terraform, CloudFormation, Kubernetes, ARM, Helm (docs.snyk.io supported-languages page); Pulumi is not listed.
So the honest replacement for `make scan` (`Makefile:494`, trivy 0.74.0 over HCL, with `.trivyignore` and the two `#trivy:ignore` decisions at `state.tf:48, 130`) is a **policy pack**, and the port must say plainly that the AWS-misconfiguration *rule library* trivy brought (AVD-AWS-0089, AVD-AWS-0132, …) is not carried over unless written. `pulumi/compliance-policies` and `pulumi/pulumi-policy-aws` (AWSGuard) exist as open-source rule libraries; AWSGuard is TypeScript (docs), which would pull a Node toolchain in for a rule set — the shape `tradeoffs.md:815-856` rejected for twenty lines of JavaScript. Write the rules this repository actually relies on in the Python pack (public-access block, ownership controls, encryption, TLS-only policy, no ACLs) and accept the trade.

**CrossGuard as "scan" and as "test" is one tool doing two jobs — say so.** In decision 3 the pack asserts the *interface* (what `plan.tftest.hcl` does); the scan rules are the *posture* checks (what trivy did). Keep them as two directories under one pack or two packs, so a green "scan" cannot be a green "test" misread.

**Packaging: uv, not pip-tools or poetry.** Verified today: Pulumi's Python runtime has first-class `toolchain: uv` (`Pulumi.yaml` `runtime.options.toolchain`, `pyproject.toml`, `.venv` default) beside `pip` and `poetry` (pulumi.com/docs/iac/languages-sdks/python/); Dependabot supports the `uv` ecosystem for version updates (GA 2025-03-13, github.blog changelog) and security updates (2025-12-16); `uv.lock` is cross-platform by construction, which closes the exact defect `.github/dependabot.yml:15-54` documents for `.terraform.lock.hcl` — a Dependabot-authored Terraform lock narrows to one platform, which is why that repository runs its own `provider-lock-refresh.yml` (`Makefile`/`validate.yml:95`). With uv the provider version is the `pulumi-aws` pin in `uv.lock` (the SDK downloads the matching plugin), so **`provider-lock-refresh.yml` has no counterpart and Dependabot `uv` replaces it**. Pin Python with `.python-version` (uv reads it) as `.terraform-version` is read by `tfenv`. Astral's Dependabot page notes open gaps (astral-sh/uv#2512) and recommends matching uv's `exclude-newer` to Dependabot `cooldown`; the July-2026 three-day cooldown default is compatible with the repository's stated preference for reviewed bumps.

**Pulumi CLI pinning is needed and has a first-class file.** `pulumi/actions` v7 has `pulumi-version` (default `"^3"` — a floating range, the opposite of `.terraform-version`) and `pulumi-version-file` ("Example: `.pulumi.version`"). Commit `.pulumi.version`, read it from the Makefile guard the way `check-terraform` (`Makefile:142`) reads `.terraform-version`, and install the CLI in workflows from that file — either via `pulumi/actions` with `pulumi-version-file` and no `command` ("install Pulumi and exit"), or a pinned `curl -fsSL https://get.pulumi.com | sh -s -- --version $(cat .pulumi.version)` guarded by `pulumi version` afterwards, as the Makefile guards zizmor (`tradeoffs.md:294-366`). The version number should move only by a reviewed PR (Dependabot cannot bump a bare version file; add it to the monthly cadence note that `provider-lock-refresh.yml` used to carry).

**Type checking.** `Pulumi.yaml` `runtime.options.typechecker: mypy` runs the checker before every `preview`/`up` (docs: "Pulumi invokes the type checker before running your program"), which makes a type error a red plan rather than a red lint — keep that on, *and* run `mypy --strict` as its own job so the failure is named. `pulumi-aws` 7.46.0 ships typed `Args` classes; strict mode is realistic.

**What stays as-is.** zizmor 1.30.1 (bump the `ZIZMOR_VERSION` pin, `Makefile:103`), `make audit-policy` (rules 4–5, `validate.yml:35-40`), actionlint, gitleaks, SHA-pinned actions, Dependabot `github-actions` group, CODEOWNERS, `pr-title`. `terraform fmt`/`validate`/tflint/terraform-docs have no object; terraform-docs's `README` inputs/outputs table maps to a generated component-interface table (e.g. from the `Args` dataclass docstrings via a small script) or is dropped with a stated reason — do not keep a `docs-check` job that checks nothing.

### (c) Revised recommendation
`ruff format --check` + `ruff check`; `mypy --strict` (and `typechecker: mypy` in `Pulumi.yaml`); pytest; `preview-offline` with the policy pack (decision 3), the pack holding a `posture/` rule set that re-implements the trivy findings this repository acted on; `trivy fs` over `uv.lock` for dependency vulnerabilities (SCA, the one job trivy can still do here, pinned as today); uv + `uv.lock` + `.python-version`; Dependabot `uv` and `github-actions` groups; `.pulumi.version` read by the Makefile guard and by `pulumi/actions` `pulumi-version-file`; zizmor + audit-policy + actionlint + gitleaks + CODEOWNERS unchanged; no provider-lock-refresh workflow.

### (d) LOCKED
**LOCKED-4:** ruff + mypy strict + pytest + a Python CrossGuard pack that carries both the interface tests and the posture rules trivy used to supply (no third-party IaC scanner reads Pulumi Python — Checkov, Trivy, KICS and Snyk verified against source/docs today), `trivy fs` kept only for `uv.lock` SCA, packaging via uv with `uv.lock` + `.python-version` and Dependabot `uv`, the Pulumi CLI pinned in `.pulumi.version` read by the Makefile guard and `pulumi/actions`' `pulumi-version-file`, and the provider-lock-refresh workflow retired because `uv.lock` pins `pulumi-aws`.

### (e) Not verified
- Whether the Pulumi CLI verifies provider plugin download checksums (relevant to the "SHA-pinned everything" posture); not researched.
- Trivy's exact minimum version for `uv.lock` (search results say v0.59.0; not re-read from release notes).
- mypy strict against `pulumi-aws` 7.46.0's generated stubs for the CloudFront/logging types used here — not exercised.

## 5. CI roles for the new repository

### (a) Proposed
The Pulumi bootstrap creates its own plan role and per-environment apply roles trusting the new repository's numeric owner/repo ids in the immutable subject format, following the same split.

### (b) Critique

**The subject half carries over unchanged and must.** `oidc.tf:62-97`: `repo:<owner>@<owner_id>/<repo>@<repo_id>:pull_request` for plan and `...:environment:<env>` for apply, measured from real tokens; `StringEquals`, `aud` conditioned (`:560-613`); the environment claim *replaces* the ref (`:80-93`), so the branch restriction lives in the GitHub Environment's deployment branch policy (README.md:482-491). The new repository's ids come from `gh api repos/<owner>/<repo> --jq '{owner: .owner.id, repo: .id}'` (`docs/BOOTSTRAP.md:107-112`). Nothing in Pulumi changes any of this.

**The plan role's backend grants get *narrower* than Terraform's, not wider.** Terraform's plan role needs to write and delete the `.tflock` sibling because a refreshing plan takes the lock (`oidc.tf:793-798, 808-818`, `plan.yml:378-384` `-lock-timeout=5m`). Pulumi's DIY `Preview` never calls `Lock` (`pkg/backend/diy/backend.go:1204-1208`; only `Update`/`Refresh`/`Destroy`/non-preview `Import` do), and `apply()` with `DryRun` constructs no snapshot manager, so nothing is persisted (`backend.go` `apply`: `if kind != apitype.PreviewUpdate && !opts.DryRun` guards the persister). What a preview reads: `.pulumi/meta.yaml`, `.pulumi/stacks/<project>/<env>.json`, and a bucket listing under `.pulumi/stacks/` (legacy-file warning scan). So the plan role is `s3:ListBucket` on the bucket plus `s3:GetObject` on those objects, with an explicit **Deny on `s3:PutObject`/`DeleteObject` over `.pulumi/*` including the lock prefix** — a stronger version of `DenyStateMutation` (`oidc.tf:844-855`), which had to leave the lock writable. Consequence: `plan.yml`'s `concurrency` block (`:44-58`) loses its "stranded `.tflock`" justification for previews; keep `cancel-in-progress: false` anyway for the comment-upsert step, and state the new reason.

**`awskms://` would have added `kms:Decrypt` to the plan role** — verified eager decryption in `pkg/secrets/cloud/manager.go` — and that is a permission on a resource the plan role runs untrusted branch code against (`oidc.tf:630-640`). Decision 1's passphrase choice removes it; record in the role comment that it is *absent because* of that choice, so a later `change-secrets-provider` knows what it has to add.

**The apply role's state grants change shape, in a way that is easier, not harder.** A `pulumi up`/`destroy` writes: the lock at `.pulumi/locks/organization/<project>/<env>/<uuid>.json` (list + put + delete, `lock.go:130-176`; the org segment is always `organization` in DIY project mode, `store.go:145-172`), the checkpoint `.pulumi/stacks/<project>/<env>.json` and its `.bak` (`state.go`), and timestamped objects under `.pulumi/history/<project>/<env>/` (and `.pulumi/backups/<project>/<env>/` unless disabled). Every one of these is under a **per-stack prefix or a per-stack filename**, so the per-environment allow is `.pulumi/locks/organization/<project>/<env>/*`, `.pulumi/history/<project>/<env>/*`, `.pulumi/stacks/<project>/<env>.json*`, and the cross-environment deny (`oidc.tf:1314`, `DenyOtherEnvironmentState`) is the same list for every *other* environment. The sibling-key problem that forced exact ARNs in Terraform (`oidc.tf:125-132, 1147-1154`: `.tflock` is a sibling, so `terraform.tfstate*` would over-match) does not arise, with one condition the bootstrap must validate: no environment name may be a prefix of another (`stage`/`staged`), or `stage.json*` reaches `staged.json`. `s3:DeleteObject` on the checkpoint stays withheld (`pulumi stack rm` is the only thing that deletes it, as `oidc.tf:1155-1160` withholds it for workspace deletion); `DeleteObject` is granted on the lock prefix only, as `HoldAndReleaseStateLock` does today. `s3:ListBucket` stays bucket-wide, unconditioned, for the reason `oidc.tf:1197-1208` gives — the backend's listing prefixes are its implementation detail — and `DenyStateBucketReconfiguration` (`:1220-1236`) carries over verbatim.

**`meta.yaml` and stack existence are bootstrap-time writes, not CI grants.** Neither role should be able to create `.pulumi/meta.yaml` or a new stack file; both exist before CI runs (decision 1). An apply role that could create arbitrary `.pulumi/stacks/<project>/*.json` would be the pattern-acquires-a-match failure `oidc.tf:1211-1219` warns about.

**Infrastructure grants are unchanged in substance.** `pulumi-aws` 7.46.0 is terraform-provider-aws v6.64.0 underneath (release notes today), so every API-behaviour finding the apply policy was written from carries over — `GetDistribution` polled after delete with no tags left (`README.md:126-132`, `docs/TEARDOWN.md` §5.5), the 90-minute deletion waiter (`tradeoffs.md:92-137`), untaggable policy types (`README.md:134-142`). The per-environment `for_each` becomes a Python loop over `environments`; the `Name`-tag conditions and both `DenyForeign*Retag` statements port as-is. One addition: the `random` provider is a separate plugin in Pulumi too (`pulumi_random`), and needs no AWS grant.

**Two things the proposal leaves implicit and the port must make explicit.** (1) `pulumi up` in `apply.yml` should consume a saved plan the way `apply.yml:349, 597` applies `terraform.tfplan` — Pulumi's `pulumi preview --save-plan` / `pulumi up --plan` exist but are documented as experimental ("The format is experimental and subject to change ... Update plans as a feature will not be deprecated"; require `PULUMI_EXPERIMENTAL=true`), and a plan cannot constrain values unknown at preview (the `random` suffix and everything downstream of it). So the prod reviewer gate approves a *preview output artefact* plus a constrained `up --plan`, with the runbook stating what the constraint does and does not cover — a weaker property than Terraform's saved plan and one the README's "approves a plan that already exists" sentence (README.md:402-406) must be reworded for. (2) `role-duration-seconds: 7200` and the `max_session_duration` argument (`oidc.tf:1112-1145`) carry over untouched — the distribution is still the clock.

### (c) Revised recommendation
Same split, same subjects, same GitHub-Environment branch policy. Plan role: `s3:ListBucket` on the bucket; `s3:GetObject` on `.pulumi/meta.yaml` and every `.pulumi/stacks/<project>/<env>.json`; explicit Deny of `PutObject`/`DeleteObject`/`DeleteObjectVersion` on `.pulumi/*` — no lock write, no KMS. Apply role `<env>`: Get/Put on `.pulumi/stacks/<project>/<env>.json*`; Get/Put/Delete on `.pulumi/locks/organization/<project>/<env>/*`; Put on `.pulumi/history/<project>/<env>/*`; bucket-wide `ListBucket`; Deny on every other environment's four prefixes; `DenyStateBucketReconfiguration` verbatim; backups disabled by env var so no grant is needed for them. Bootstrap validates that no environment name prefixes another. Infrastructure and identity policies ported statement-for-statement from `oidc.tf`, with the same SIDs so `docs/TEARDOWN.md` §5.4–5.5 cross-references survive.

### (d) LOCKED
**LOCKED-5:** Same plan/apply split and immutable-subject trust as `bootstrap/oidc.tf`, but the plan role holds **read-only** backend access with an explicit deny on all `.pulumi/*` writes — the DIY backend's `Preview` takes no lock and persists nothing (verified in `pkg/backend/diy/backend.go`) and the passphrase provider needs no `kms:Decrypt` — while each apply role's grants and cross-environment denies are expressed as per-stack prefixes under `.pulumi/{stacks,locks/organization,history}/<project>/<env>`, with `meta.yaml` and stack files created by the bootstrap rather than by CI, and `up --plan` documented as experimental and value-limited rather than sold as Terraform's saved plan.

### (e) Not verified
- The exact S3 API calls (and whether `ListObjectsV2` is issued with a `.pulumi/stacks/` prefix or bucket-root) a `pulumi preview` makes on the current CLI — read from source, not captured from CloudTrail. `iam simulate-principal-policy` on the ported policies, as `tradeoffs.md:665-676` did, is the verification step.
- Whether `pulumi up` writes stack tags into the checkpoint on the DIY backend (would be covered by the checkpoint `PutObject` either way).
- `up --plan` behaviour against this resource set with unknown values was not exercised.

## Cross-cutting findings the port must preserve (outside the five decisions)

1. **The deploy contract is byte-exact and the app repository cannot see this one.** `docs/DEPLOY_CONTRACT.md`: role `arn:aws:iam::<account>:role/react-cloudfront-app-deploy-<env>` at the root path with the mandatory boundary (`:56-81`); trust subject `repo:<owner>@<id>/react-cloudfront-app@<id>:ref:refs/heads/main`, `StringEquals`, no GitHub Environment on the deploy job (`:141-203`); three `String` parameters at `/static-site/<env>/{bucket_name,cloudfront_distribution_id,site_url}` read one at a time with `ssm:GetParameter` singular (`:232-263`); `site_url` published whole; CSP string agreed across repositories and the app refuses to deploy on drift (`:501-570`); effective permissions = inline policy ∩ boundary, checked only by a real deploy (`:571-680`, `oidc.tf:2440-2472`). The Pulumi component must produce identical strings; the policy pack asserts them (decision 3).
2. **Tagging is the teardown's eyesight.** `Project` and `Env` on *both* provider instances (`envs/stage/providers.tf:13-44`; `modules/static-site/tags.tf:45-62`: a missing `default_tags` on the `us-east-1` alias yields four untagged CloudWatch resources invisible to the sweep). Pulumi's `aws.Provider(default_tags=...)` must be set on both explicit providers and the component must read them back (`aws.get_default_tags` exists in `pulumi_aws`) and fail the preview when `Project` is empty or `Env` ≠ the stack's environment — Pulumi has no `precondition`, so raise in the component. `ManagedBy` becomes `pulumi`.
3. **The sweep's queries and quota counters.** `docs/TEARDOWN.md` §6 rows 1–11 and §6.1: `list-cache-policies --type custom`, `list-response-headers-policies --type custom` (20-per-account quotas), `list-functions` filtered on `<name_prefix>-site-`, log groups under `/aws/vendedlogs/cloudfront/<name_prefix>-site-*` in **us-east-1**, delivery sources/destinations/deliveries in us-east-1, tagging API on `Project`+`Env` in **both** regions (`e2e.yml:1236-1238`; `tradeoffs.md:581-622`), and the machine-readable `verify-teardown-result: clean|leak|incomplete` last line (`TEARDOWN.md:481-500`). `make verify-teardown` reads its values from `envs/*/terraform.tfvars` and `main.tf`; the port reads them from `Pulumi.<env>.yaml`. The stranded-lock row becomes "an object under `.pulumi/locks/`", cleared by `pulumi cancel`.
4. **Bootstrap teardown ordering and `prevent_destroy`.** §8 phases 0–2: boundary unattached first (IAM `DeleteConflict`), empty the versioned bucket (versions *and* delete markers, now including `.pulumi/history` objects), then remove the guard. Pulumi's `protect=True` is the analogue of `prevent_destroy`, but `pulumi state unprotect --all` removes it from the CLI without a source edit — weaker friction than `state.tf:57-66` argues for. Document that the runbook's phase 2 is `pulumi state unprotect` + `destroy`, and that nothing in Git records it — which is what that comment wanted.
5. **Everything is deployed from a workflow, nothing on merge; `prod` is hand-verified and outside e2e** (README.md:402-406, 502-505). `e2e.yml`'s "armed"/"clean" outputs and `if: always()` cleanup shape (`tradeoffs.md:506-545`) port unchanged; the `/assets/e2e-cache-probe.js` upload and the `/assets/does-not-exist.js` 403 assertion (`tradeoffs.md:624-651`, README.md:249-254) are contract tests, not Terraform tests.
6. **`force_destroy = true` lives in the environment root, not the module** (README.md:471-480); the Pulumi stack config carries it and the component refuses a default of `True`.
7. **`wait_for_deployment = true`** on the distribution is why no wait-for-Deployed step exists (README.md:254-255); the Pulumi resource has the same argument — keep it, or `e2e.yml` gains a wait.
8. **The local-operator mirror** (`tradeoffs.md:233-244`; user memory): the hand-managed `isai2105-local-operator` role mirrors the apply policies SID-by-SID. A new set of Pulumi roles means either a second mirror or a note that the local operator is not mirrored for the port; do not merge the two.
9. **`.github/dependabot.yml`'s argument against the `terraform` ecosystem** (`:15-54`) becomes an argument *for* `uv`: state the reversal where the old argument was, so a reader does not carry the Terraform-era rule across.
10. **Custom-domain path is plan-verified only** (README.md:512-516); the port keeps `certificate.tf`'s branch and labels it the same way — the offline preview (decision 3) is exactly the level of verification it has today.
